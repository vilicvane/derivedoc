# 对话捕获

**依据**：[对话如何进入文档](../source/capture.md) · [两层文档的边界](../source/two-layers.md)

目标分两步落地：当前阶段只在用户消息进入主会话前，由子会话判断并沉淀 source；下一步把
思考产物留在 pending，并在捕获完成后只把产物位置告诉主会话，不注入全文。如果上下文里有
derivedoc 的提示，完成通知同时原文附上该提示。完整链路最终让「agent 没回头查」不再依赖
agent 自觉。

## 实现状态

已完成（Codex 适配）：

- `UserPromptSubmit` 钩子：先做一次向上查找 `.derivedoc` 的廉价判定，不在工作区直接放行。
- 钩子是**阻塞**的：实测钩子 sleep 6s，整轮耗时从 5.6s 变成 10.7s。整条链路依赖这一点
  ——子会话必须在主模型开始生成之前跑完。
- `capture.mjs`：从钩子 payload 取 `session_id` / `cwd` / `prompt`，用
  `codex exec fork <session_id> --ephemeral` 起一次性子会话，限定
  `sandbox_mode=workspace-write` 且可写根只有工作区；子会话的最终回复落在
  `.derivedoc/pending/`，运行记录落在 `.derivedoc/capture.log`。
- 钩子配置里的 `timeout` 必须放宽（当前 600s）。默认 15s 会把捕获子会话掐断，表现是静默
  失败、pending 里没有产物。
- 递归防护：子会话进程带 `DERIVEDOC_CAPTURE=1`，钩子看到就直接放行。

未完成：把 pending 里的思考位置回传主会话，并在有 derivedoc 提示时原文附带提示。

已知成本：一次捕获要 80–160 秒（子会话继承主会话上下文后跑一轮完整推理），这段时间用户
在等。后续优化方向：换更小的模型、缩小给子会话的上下文，或先用廉价判定筛掉不需要捕获
的消息。

## 判定与展开

- 不是每条消息都值得展开：局部细节调整这类既不必进入 source，也不必进入主会话上下文。
- 影响 derived 方案的消息分两类：与主会话当前工作相关的，主会话要知道展开细节；无关的
  后台记录即可。
- 判断与展开的过程不放在主会话里——既打断它的工作线程，也让过程细节占用它的上下文。

## 交付形态

- 思考产物仍是完整但精简的思考过程：按时间顺序，含中间结论与转折原因，能作为主会话
  自身思考的延续，而不是要点报告。判据是「raw 内容消失后，下一位有能力的 agent 能否不
  重复调查、设计或推导地继续」。
- 思考产物以主会话的第一人称落地，形式上像它自己想过的。
- 捕获完成后只把思考产物的位置告诉主会话，不把全文注入 model-visible history；如果上下文
  里有 derivedoc 的提示，完成通知同时原文附上该提示。

## 时序

- turn 开始：先跑子会话，再把思考产物位置交给主会话，然后启动 turn；主会话需要时自行读取。
- steer：turn 已经在跑，模型可能正在生成。统一做法是把用户消息的可见化也交给同一套
  流程：先拦下消息，等思考就绪后再连同产物位置一起交付。steer 因此会等子会话，这是预期
  行为。
- 派生落地在关键路径上，需要排队时子会话就等着，不插队。
