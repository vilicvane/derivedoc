# 通知、排队与收敛

**依据**：[通知、排队与收敛](../source/session-sync.md) · [人与 agent 的接口](../source/interfaces.md)

## 谁会被通知

- 正在工作的会话：收到「大致发生了什么更新」的通知；如果与它的工作内容相关，由它确保
  derived up-to-date，并自行决定继续原工作还是调整。
- 空闲会话：不做即时通知，等它下次收到用户消息时把期间的更新合并进注入内容。

两种情形都需要 derivedoc 记录「每个链接过的会话已知到哪个版本」，否则算不出增量与
diff 基准。

## 通知内容

source 变更的通知用行级 diff，以该会话上次已知版本为基准；不附带额外上下文或定位信息，
由 agent 自己决定后续怎么读。

实测（Codex）：向空闲线程投递一条消息会立刻开一轮并回应，也就是「通知」等价于「让那个
会话跑一轮」；会话在忙时排队。因此通知是有成本的动作，发送前要判断相关性。

## 派生排队

- agent 更新 derived 一律排队，一个一个来，避免并发写。
- 执行者是收到通知的会话，队列只做互斥。
- 用户在 web 上更新 source 直接生效，并同步更新排队中的任务。
- 用户消息触发的派生任务优先于后台任务；用户任务之间按到达时间；后台任务只在没有用户
  任务等待时执行。
- 已知风险：持锁会话卡住（等用户、等模型、出错不退）会堵住所有人的用户消息，需要单独的
  超时或回收策略。

## 收敛

取「先落地再排队」：不做事前校验，也不追求 derived 永远最新。正在更新 derived 的会话，
如果依据的内容在过程中变了，完成后重新检查、必要时再排一次。文档本身就是 source of
truth，短暂偏离可以接受。
