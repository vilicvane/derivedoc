# 对话如何进入文档

**落地**：[对话捕获](../derived/capture.md) · [Codex 适配](../derived/harness-codex.md)

## 决定：会影响 agent 行为的用户消息都算 source

先按这个标准执行，效果好不好等实践检验。

## 决定：用户消息之后 fork 主会话来写 source

理想流程是：用户消息进入上下文 → fork 出子会话 → 子会话更新 derivedoc → 把精简结果
注入主会话，作为对这条消息的回应开头。fork 出来的总结会话是 agentic 的，自己获取
相关上下文。

## 决定：交回的是思考过程，不是要点报告

要完整但精简、按时间顺序、包含中间结论与转折原因，能作为主会话自身思考的延续接上去。

## 决定：思考以主会话的第一人称落地

形式上像主会话自己想过的；log 层面仍能看出这条内容来自注入。

## 决定：turn 开始与 steer 走同一套流程

两者都先拦下用户消息，等思考就绪再一起交付。steer 等待子会话是预期行为，不是代价——
用户本来就希望 agent 真正理解这句话的影响之后再继续。

## 决定：编排由 derivedoc 自己提供 harness 适配

适配负责拦住用户消息、跑子会话、更新文档、把思考注入主会话可见历史、再启动 turn。
每个 harness 一份适配。

## 决定：捕获链路先只覆盖 source 沉淀

当前阶段只完成用户消息中的决定判定与 source 落地；思考注入主会话放到下一步。

## 决定：注入优先用 thread/inject_items

把思考追加到主会话的 model-visible history，不做 surface replacement。

## 决定：捕获完成后只回传思考位置

捕获完成后只把思考产物的位置告诉主会话，不注入思考全文——需要时由主会话自己去读。

## 决定：保留对话记录用于 source 溯源

对话记录作为 source 决定的溯源依据，需要能回答某条决定是谁在什么时候说的。
