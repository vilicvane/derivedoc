# 对话如何进入文档

## 影响 agent 行为的用户消息都算 source

先按这个标准执行，效果好不好等实践检验。

## 用户消息之后 fork 主会话来写 source

用户消息进入上下文 → fork 出子会话 → 子会话更新 derivedoc → 把精简结果注入主会话，作为对这条
消息的回应开头。fork 出来的总结会话是 agentic 的，自己获取相关上下文。

## 交给主会话的是思考过程，不是要点报告

完整但精简、按时间顺序、包含中间结论与转折原因，能作为主会话自身思考的延续接上去。

## 思考以主会话的第一人称落地

形式上像主会话自己想过的；log 层面仍能看出这条内容来自注入。

## turn 开始与 steer 走同一套流程

两者都先拦下用户消息，等思考就绪再一起交付。steer 等待子会话是预期行为——用户本来就希望
agent 真正理解这句话的影响之后再继续。

## 编排由 derivedoc 自己提供 harness 适配

适配负责拦住用户消息、跑子会话、更新文档、把思考注入主会话可见历史、再启动 turn。每个 harness
一份适配。

## 对话记录作为溯源依据保留

用户对话要保留下来，用来回答「source 里这条决定是谁在什么时候说的」。日志是本地缓存，不进版本库。

TODO: 思考注入尚未实现，当前只把产物位置回传给主会话。
TODO: 钩子安装或修改后需要新开会话才生效，界面上还没有提示。

## Codex 捕获钩子放在项目级

derivedoc 的 Codex 捕获钩子只放在项目级 `.codex/hooks.json`，用户级 `$CODEX_HOME/hooks.json` 不再保留该钩子。

## 先判定承诺状态再沉淀

捕获子会话在任何写入前先逐项判断用户是否已经作出承诺。明确要求实施、规定最终行为或明确采用此前方案才算已确认；考虑、比较、假设、提问、请求分析和事实描述都不算。方案描述得具体不能替代承诺；“你说得对”默认只确认判断或事实，只有“就按这个方案做”等明确表达才采用方案。没有已确认内容时不改文档是正常结果。

## TODO 只来自已确认且未完成的要求

只有用户已经确认、要求产生可观察的项目状态变化，并且检查后确认尚未完成的要求才能生成 TODO。讨论中的候选方案、分析请求和 agent 自己建议的后续工作不能生成 TODO。
