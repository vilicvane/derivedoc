# 两层文档的边界

## source 沉淀决定

沉淀的是决定，不是结论，更不是推理过程。判据是能不能从别处重新推导：决定是人做的选择，
推不出来；结论是推理的产物，依据还在就能重推。

## source 读起来像精简的产品内部手册

一页一主题，讲清「是什么、为什么、边界在哪」，不是会议纪要。怎么组织文件由用户决定：可以写在
一个文件里，也可以分散成很多文件，或用链接串起来。

不要给每条都套「决定：」前缀；一件事一个 `##` 小节，直接写规则。还没做的事单独一行标
`TODO:`，做完了就把那行删掉——文档里看不出哪些没做，就等于没有待办。

待办状态由正在执行相关工作的 agent 主动维护，不等用户提醒。完成工作时检查相关 source 和
derived：确认完成就删除对应 `TODO:` 并同步实现状态；部分完成就把待办改写成剩余缺口。只有能从
代码、配置或运行结果确认完成时才清除待办。

## derived 由 agent 根据 source 维护

落地阶段 agent 可以根据实际进展灵活调整 derived。

## 两层之间用链接互相引用

source 里指向落地的 derived，derived 里指向依据的 source。不用 frontmatter 字段做结构化覆盖
追踪，链接本身就是关系。

## source 在落地阶段原则上不动

只有用户明确授权 agent 自行处理（比如无值守开发）时才允许改。这时必须有合适的 diff 展示机制，
或者先追加为未合并的 source 条目，等用户交互时再合并。

## 文档的提交由人确认

agent 可以改文档、可以暂存，但提交这个动作要人来做——文档是给人确认的产物，未经确认就提交
等于绕过审阅。agent 提交代码时也不要把文档一起带上。

## 中文用「派生」对应 derived

代码、目录和标识符里仍然用 derived。

## 待办维护提示词按项目承载

derivedoc 可以提供项目模板文件；具体如何维护待办项的提示词放在项目自身的文档中，由项目定义这部分规则。
